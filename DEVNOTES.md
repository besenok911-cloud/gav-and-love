## 2. Як публікувати зміни

- **Сайт**: push у `main` → GitHub Pages оновлюється за ~1 хв. HTML кешується 10 хв, тому для перевірки додавайте `?cb=…`. CSS, JS і дані підключені з версією `?v=N` — після зміни файлу підніміть N у `index.html`, інакше телефони покажуть старе.
- **Воркер**: `cd worker && npx wrangler deploy`. Якщо у `wrangler.toml` зʼявився блок `[[r2_buckets]]`, бакет `gavlove-photos` має існувати до деплою — інакше падає весь деплой, а не лише фото. Секрети (токени бота, календаря, паролі) — тільки через `wrangler secret`, ніколи у файлах репозиторію. Змінні `ALLOW_ORIGIN`, `SITE_URL` — у `worker/wrangler.toml`.
- **База**: `npx wrangler d1 execute gavlove-crm --remote --command "…"` для коротких ASCII-запитів, `--file` для UTF-8; помилки авторизації 10000 / 7403 бувають тимчасові — повторити.
- `/catalog` і `/site` кешуються 60 с; перший рендер сайту бере `data/catalog.js`, після зміни цін перегенеруйте снапшот з живого `/catalog`.

## 3. Бекенд — ключові рішення

- **Авторизація**: таблиці users / sessions (PBKDF2), ролі owner → admin → master. Клієнти окремо: `client_sessions` (90 днів) + одноразові коди `client_otp` (3 коди на клієнта та 10 на IP за 10 хв; для невідомих номерів — нейтральна відповідь).
- **Записи**: таблиця bookings; статуси new / confirmed / arrived / in_progress / done / paid / no_show / waitlist / cancelled; `source` (site / phone / instagram / telegram / other); `event_id` події Google Calendar. CRM — джерело істини для календаря: редагування запису оновлює подію, скасування видаляє.
- **Слоти**: `/slots` рахує вільний час на майстра з урахуванням тривалості послуги, робочих годин, обідів, вихідних і відпусток; перенесення передає `exclude=<id>`, щоб власна подія не блокувала слот. Обмеження: не раніше ніж за 2 год, не далі ніж на 30 днів.
- **Крони** (wrangler `[triggers]`): щодня о 16:00 UTC — дайджест салону і нагадування клієнтам за день; кожні 30 хв — «візит незабаром». Перенесення скидає прапорці `remind_*`, і клієнт отримує нагадування повторно.
- **Бот**: запис, `/visits` (картки з кнопками Перенести / Скасувати), `/cabinet` (одноразове посилання в кабінет). **Єдине підтвердження особи — кнопка «Поділитися номером»**: бот приймає лише власний контакт відправника (звіряє user_id), за номером знаходить або створює картку клієнта і прив'язує чат. Посилання з коду запису (`?start=<код>`) саме по собі нікого не підключає. Крок «дайте номер» пам'ятає, куди повернутись (запис / кабінет / візити). Сповіщення клієнтам: створено / підтверджено / перенесено / скасовано; ручне повідомлення та розсилка з CRM.
- **Послуги**: додаткові послуги мають колонку «Для кого» (собаки / коти / усі) і в формі та в CRM показуються лише під вид тварини.
- **Фото тварин**: підписи в таблиці `pet_photos`, байти — у **R2-бакеті `gavlove-photos`**, якщо у воркера є binding `PHOTOS`: ключ `pets/<pet_id>/<token>.<ext>` зберігається в колонці `r2_key`, розмір — у `size`. **Без біндингу** (так воно й працює зараз, див. нижче) байти пишуться в колонку `data`, як і раніше, з лімітом 900 КБ; з бакетом ліміт 5 МБ. Публічний URL той самий — `/photo/<id>/<token>`, кеш на рік; якщо бакет недоступний, а копія в `data` ще є, воркер віддасть її. Видалення запису (клієнтом, майстром, адміністратором, а також каскади при видаленні улюбленця чи клієнта) прибирає і файл з бакета. Позначка 🌐 (published) на фото «До» і «Після» одного дня → пара з'являється на сайті через `/before-after`.
- **Стан на 20.09.2026**: R2 увімкнено, бакет `gavlove-photos` створено (регіон eeur, поруч із базою), воркер задеплоєно з біндингом `PHOTOS`, єдине наявне фото перенесено — у D1 не лишилось жодного байта зображень. Нові фото одразу йдуть у бакет.
- **Два розміри одного фото**: браузер (CRM, кабінет майстра, кабінет клієнта) з одного відкриття файлу робить **велике** (довга сторона 1600, якість 0.85) і **мініатюру** (560, 0.72) і надсилає обидва в одному запиті (`data` + `thumb`). Мініатюра лягає окремим обʼєктом `pets/<pet_id>/<token>-t.<ext>` (колонки `thumb_key`/`thumb_size`) і віддається за адресою **`/photo/<id>/<token>/t`**. Усі сітки, стрічки й аватарки беруть мініатюру, а посилання «відкрити фото» і лайтбокс на сайті — велике. Якщо мініатюри немає або її файл зник із бакета, `/t` віддає велике, тож нічого не ламається. Мініатюра — не привід втратити фото: якщо вона не зчиталась чи не збереглась, запис просто лишається без неї.
  - **Мініатюра обмежена по КОРОТКІЙ стороні** (560 px, довга — не більше 1120): плитка галереї квадратна і обрізає фото по короткій стороні, тож обмеження по довгій робило б зображення розмитим на екранах з високою щільністю. Портрет 3:4 дає 560×747 (~15–45 КБ), альбомний — 747×560, квадрат — 560×560.
  - Мініатюра малюється **з уже зменшеної великої копії** (крок ~2×, а не ~7×) і з `imageSmoothingQuality="high"` — інакше хутро «сиплеться».
  - Один розмір мініатюри на всі місця — свідомо: аватарка 84 px отримує ті самі ~30 КБ, що й плитка. Третій розмір подвоїв би кількість обʼєктів і записів у бакет заради кількох кілобайт; усі дрібні картинки мають `loading="lazy"`, тож поза екраном вони не вантажаться.
  - Колонки для наявної бази додаються вручну: `ALTER TABLE pet_photos ADD COLUMN thumb_key TEXT;` і `ADD COLUMN thumb_size INTEGER;` (у `schema.sql` вони вже описані для нової бази).
- **Перенесення старих фото**: `POST /admin/photos-to-r2` (лише власник, тіло `{"limit":25}`) — кладе файл у бакет, звіряє розмір і лише тоді очищає `data`; викликати можна скільки завгодно разів, вже перенесене не чіпається. Зараз переносити нічого, але якщо десь зʼявиться стара база — порядок той самий.
- **Якщо доведеться піднімати все з нуля** (новий акаунт, передача власнику): увімкнути R2 у панелі Cloudflare (це платіжна опція, з CLI не вмикається) → `npx wrangler r2 bucket create gavlove-photos` → лише після цього `npx wrangler deploy`, бо біндинг на неіснуючий бакет валить увесь деплой.
- **CMS сайту**: `index.html` розмічено `data-cms-section` (9 блоків можна сховати) і `data-cms="ключ"` (≈106 текстів); вкладка «Сайт» у CRM зберігає все у `settings.site_cms`, сайт застосовує через `GET /site`.

## 4. Фронтенд — правила, яких дотримуємось

- **Форма запису — майстер із 4 кроків** (улюбленець → послуга → дата й час → контакти). Стан кроку рахується з даних (`stepDone`), відкритий лише поточний крок, наступні заблоковані, «Далі» вмикається на заповненому кроці, вибір часу веде далі автоматично. Зміна попередньої відповіді знецінює залежні (нова послуга скидає обраний час), тож застарілий слот надіслати неможливо.
- **Підстановка для постійних клієнтів**: якщо на пристрої є сесія кабінету — ім'я, телефон і улюбленці з `GET /client/me` (порода й вага підставляються після вибору послуги); інакше — знімок останнього запису з `localStorage` (`gl_booking_prefill`). Прапорець «Запам'ятати мене на цьому пристрої» (увімкнений) керує локальним знімком, знімок живе 60 днів, а «Це не я» стирає і знімок, і сесію кабінету на цьому пристрої. Ручний вибір породи/ваги заміщає запам'ятаний, вибір іншого улюбленця скидає породу й вагу, а якщо список часу не завантажився — заявка йде без часу (не в лист очікування).

- **Телефон завжди зберігається як `+380XXXXXXXXX`** — незалежно від того, як його ввели на сайті, у CRM чи в боті. На екрані показується згрупованим (`+380 67 111 00 13`), у посиланнях і вивантаженнях — без пробілів. Рядки, які не читаються як номер, лишаються як є.
- **Фото улюбленця може додати клієнт** (кабінет), майстер (картка візиту) і салон (CRM). Клієнт не може видалити фото, зроблене на візиті або вже опубліковане на сайті. Ліміти на клієнта: 20 карток тварин, 40 фото.
- **Форма запису підставляє породу й вагу з картки** і за ними пропонує послугу. Вага з картки («10–15 кг») зіставляється з прайсовими смугами («до 20 кг») за кілограмами; якщо діапазон не вміщається в одну смугу, вибір лишається за клієнтом.
- **Галерею наповнюємо з картки тварини** (правило власника): позначене 🌐 фото стає плиткою галереї, а «До»+«Після» одного дня — плиткою з повзунком. Вид тварини береться з картки. Майстер додає фото зі свого візиту сам (кнопки на картці візиту), публікує на сайт лише власник або адміністратор.
- **Вид тварини у галереї** визначається за самим фото, а не за підписом до поста в Instagram (саме через підписи коти й собаки колись перемішались). Фото без тварини (інтерʼєр, вхід, засоби) не мають виду і показуються лише у «Усі».
- **Галерея**: фото з `data/gallery.js`, звичайні відео з `data/videos.js`, ролики «До / після» з `data/beforeafter.js` (плитка-відео з бейджем «✨ До / після · кличка · порода», у лайтбоксі — підпис), пари з CRM — плитка з повзунком. У режимі «Усі»: ролик після кожного 5-го фото, інше відео після кожного 7-го. Кожен ролик присутній лише в одному наборі.
- **Головне фото** не має повторюватись у інших блоках сайту. Зараз — пост 119 (грумерка з акітою), його копію з галереї прибрано. При заміні: кроп 4:5, ~1200×1500 WebP у `assets/people/`, нова назва файлу (кеш), прибрати дубль з галереї.
- **Лайтбокс на телефоні**: сцена не вища за 70dvh і зі відступом згори, бо iOS малює власні кнопки плеєра поверх сторінки — наші кнопки не повинні потрапляти в прямокутник відео. Кнопка закриття підписана «Закрити», бейдж ролика стоїть над відео. Правила лежать останнім блоком у CSS, щоб перебивати десктопні.
- **Телефони**: пресети періодів у CRM — завжди в один рядок; списки у футері — два рівні стовпчики; головне меню згортається в бургер нижче 1100px; `html, body { overflow-x: clip }`, щоб сторінку не можна було посунути вбік.
- **Вага сторінки**: плитки галереї показують мініатюри `assets/gallery/t/` (560 px, ~24 КБ), повне фото відкривається лише в лайтбоксі; фото «Простору» — `assets/interior/t/` (760 px) з `data-full` на оригінал. Після зміни фото перегенеруйте мініатюри і підніміть версію `data/gallery.js?v=`.
- **Галерея відкривається порціями** по 24 плитки («Показати ще»), а не всі 242 одразу; плитки поза екраном браузер не малює (`content-visibility`).
- **Ролики самі програються лише на великих екранах** і при нормальному зʼєднанні, по одному найвиднішому. На телефоні показується кадр-обкладинка, відео вмикається у лайтбоксі.
- **Відео**: реенкод у 540p (H.264, crf 28, faststart) через ffmpeg із пакета `imageio-ffmpeg`; постер — перший кадр у WebP.
- **Локальна перевірка CRM** без бекенда: скрипт складає `_crm_mock.html` (у git не входить) із записаними відповідями API; сайт і CRM зручно дивитись через `python -m http.server 8899`.

## 5. Технічні пастки

- Windows: `git merge` переписує файли у CRLF — перед багаторядковими замінами нормалізуйте у LF.
- `.claude/` ігнорується git (робочі копії агентів одного разу потрапили в коміт).
- Тимчасові QA-акаунти створюйте лише на час тестів і видаляйте разом із сесіями; паролі власника та адміністратора не скидати.
- `curl` на Windows псує кирилицю в тілі запиту — API тестуйте з Node або Python.
- Telegram-тести з CRM/бота відправляють реальні повідомлення прив'язаним клієнтам.
